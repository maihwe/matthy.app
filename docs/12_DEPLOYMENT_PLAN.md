## 1. Environments (§40)

| Environment | Purpose | Data | Access | Lifetime |
|---|---|---|---|---|
| **Development** | Local work | Synthetic, generated by `scripts/` | The builder's machine | Persistent |
| **Testing** | Automated test runs | Created and destroyed per run | CI only | Ephemeral |
| **Staging** | Pre-production verification | Production-shaped, anonymised | Builder | Persistent |
| **Production** | Live | Real | Deploy pipeline only | Persistent |

Two rules that distinguish a serious deployment from a convenient one:

**Production is never a development target** (§40). No production credential exists on a
development machine, no local config points at the production database, and the
temptation to "just check one thing" is removed by making it impossible rather than
discouraged.

**Staging is production-shaped.** A staging environment with different instance sizes,
a different PostgreSQL major version, or no Redis is not a rehearsal — it is a
different system that happens to run the same code, and it will pass changes that
production rejects. Staging mirrors production's topology, scaled down but not
simplified.

## 2. Containerisation (§40)

Four images, one per process role. The application code is identical across all four;
only the entrypoint differs.

| Service | Role | Scales |
|---|---|---|
| `web` | Django + ASGI (gunicorn/uvicorn) | Horizontally |
| `worker` | Celery worker | Horizontally, per queue |
| `beat` | Celery beat scheduler | **Exactly one** |
| `db` | PostgreSQL (+ Redis as a managed service) | Vertically, then replicas |

**`beat` must never run more than one instance.** Two schedulers means every scheduled
task fires twice — duplicated reminders at best, duplicated financial sweeps at worst.
It is a singleton by design, and the deployment must enforce it rather than assume it.

### 2.1 Image discipline

- Multi-stage build: build dependencies do not reach the runtime image.
- Non-root user.
- Pinned base image digest, not a floating tag — `python:3.12-slim` changes under you.
- Dependencies pinned with hashes (`pip-compile --generate-hashes`).
- Read-only root filesystem where possible; `/tmp` as a tmpfs.
- Healthcheck on each service, distinct from liveness (a `web` container that can serve
  but not reach the database is unhealthy, not dead).

## 3. Local development (§40)

`docker-compose up` brings up the full stack — `web`, `worker`, `beat`, `postgres`,
`redis`, `mailhog` — so that a developer's machine has the same topology as production.
An environment that differs locally is one where "works on my machine" is a real
category of bug, and the fix is to remove the difference rather than to add a caveat.

`docker-compose.override.yml` (git-ignored) carries machine-specific settings;
`docker-compose.yml` is committed and shared.

Seed data comes from `scripts/seed_dev.py` — generated, synthetic, and including a
realistic Nigerian location tree and enough members and schemes to exercise the
collector dashboard. Never from a production dump (11 §5.1).

---

## 4. Configuration and secrets

Follows 10 §7 in full. Deployment-specific points:

- Configuration is read from environment at process start; a missing required variable
  fails the boot loudly rather than defaulting to something insecure.
- Secrets come from the platform's secret store and are injected at runtime, never
  baked into an image. An image that contains a secret is a secret in every registry
  and every cache that holds it.
- Separate secret sets per environment; a staging credential cannot open production.
- `DJANGO_DEBUG` is `False` in staging and production, asserted at boot — a debug page
  in production exposes settings, source, and often credentials.

## 5. CI/CD pipeline

Builds on 11 §6. The deployment stages:

```
push / PR
   │
   ▼
[ CI gates — 11 §6 ]──────────► fail = stop
   │
   ▼
Build image ──► scan ──► push to registry (tagged by commit SHA)
   │
   ▼
Deploy to staging ──► run migrations ──► smoke tests ──► integration tests
   │
   ▼
Manual approval
   │
   ▼
Deploy to production ──► migrate ──► health check ──► monitor
```

**Images are tagged by commit SHA**, never `latest`. A deploy that cannot name the exact
commit it is running cannot be rolled back reliably, and rollback is the only thing that
matters during an incident.

### 5.1 Migration ordering

Migrations run as an explicit step **before** the new application version receives
traffic, and must be:

- **Backward compatible** with the currently-running version, so a rollback does not
  require a database rollback. The expand/contract pattern: add a column, deploy code
  that writes both, backfill, deploy code that reads the new one, drop the old one in a
  later release.
- **Reversible where possible**, with the irreversible ones called out in the PR.
- **Never run implicitly on application start.** Two containers starting simultaneously
  must not race to migrate; migrations are a single, controlled step.

For financial tables, 03 §16's stricter discipline applies on top of this.

## 6. Deployment strategy

**Rolling deployment** with a health check gate: new instances must pass
`/health/ready` before old ones are drained. A deploy that fails its health check rolls
back automatically rather than leaving a half-updated fleet.

| Concern | Approach |
|---|---|
| Zero downtime | Rolling update; connections drained gracefully; long-running requests allowed to finish |
| Rollback | Previous image SHA redeployed; under 5 minutes |
| Feature flags | Used for changes that cannot be rolled back by image alone (a schema-dependent feature) |
| Celery workers | Drained before replacement; in-flight tasks finish or requeue safely (02 §5.5) |
| `beat` | Replaced with a brief scheduled-task blackout, since two schedulers must never overlap |

**Deploys do not happen during high-traffic windows.** For a daily-collection platform
that is a specific window — collectors record in the early morning and evening. §39's
capacity planning and §38's load testing inform when that is.

## 7. Observability (§40)

### 7.1 Centralised logging

| Requirement | Detail |
|---|---|
| DEP-LOG-001 | Structured JSON logs, shipped off-host with an application user that cannot rewrite them (10 §8). |
| DEP-LOG-002 | Correlation IDs propagate from request through Celery task to completion, so one logical operation is traceable across processes. |
| DEP-LOG-003 | **Logs never contain** passwords, PINs, tokens, full account numbers, or unredacted PII (10 §5.2). |
| DEP-LOG-004 | Financial operations log the reference, the amount, and the outcome — enough to reconstruct a dispute without exposing the actor's credentials. |
| DEP-LOG-005 | Retention meets the applicable regulatory requirement (14). |

DEP-LOG-002 is what makes the rest usable. Without it, an HTTP request that enqueues a
Celery task that calls a payment provider produces three unrelated log streams, and
debugging a failed payment becomes archaeology.

### 7.2 Monitoring and alerting

| Category | Signals | Alert threshold |
|---|---|---|
| **Financial integrity** | Ledger balance check failures; `outstanding_*` reconciliation drift (03 §9.3.1); unbalanced transaction attempts | **P1 — page immediately** |
| **Money movement** | Payment success rate, webhook processing lag, failed disbursements | P1 on rate drop |
| **Availability** | Uptime, error rate (5xx), latency p50/p95/p99 | P1 on sustained error rate |
| **Database** | Connection saturation, slow queries, replication lag, lock waits, deadlocks | P2, P1 on lock contention affecting financial writes |
| **Queues** | Celery queue depth, task failure rate, task latency | P2; P1 if financial tasks are backing up |
| **Infrastructure** | CPU, memory, disk, disk IOPS | P2 |
| **Security** | Failed-login spikes, refresh-token reuse detection, permission-denied spikes | P1 on reuse detection (10 §3.1) |

**The financial-integrity alerts outrank everything else on this list.** Availability is
recoverable; a ledger that has drifted is a correctness incident with legal and
interpersonal consequences. A pager that fires for a slow dashboard before it fires for
a reconciliation mismatch is configured wrongly.

### 7.3 What is never used as a monitoring shortcut

No health check that only asserts the process is running. A `web` container that cannot
reach PostgreSQL, or a `worker` whose broker connection has silently died, is unhealthy
and must report as such.

## 8. Backup and disaster recovery (§44 rules 14, 15)

§44 rule 15 — *"Test restoration of backups"* — is the requirement most often claimed
and least often performed. An untested backup is a belief, not a control.

### 8.1 Backup

| Requirement | Detail |
|---|---|
| DEP-BAK-001 | Continuous WAL archiving plus a nightly base backup, giving point-in-time recovery. |
| DEP-BAK-002 | Backups encrypted with a key **distinct** from the database's (10 §5.1). |
| DEP-BAK-003 | Stored in a separate region and a separate account from production, so a single compromised credential cannot destroy both the data and its copies. |
| DEP-BAK-004 | Retention: 30 days point-in-time; monthly full retained 12 months; financial-year-end retained per the regulatory requirement in 14. |
| DEP-BAK-005 | **Object storage for documents is backed up separately** — the database holds references, not files. |
| DEP-BAK-006 | Backup success and age are monitored; a backup that has not run is a P1. |

DEP-BAK-003 is not paranoia. The most common way an organisation loses both its data and
its backups is that whoever deleted one had credentials to the other.

### 8.2 Recovery objectives

| Objective | Target | Notes |
|---|---|---|
| **RPO** (max data loss) | **≤ 5 minutes** | Point-in-time recovery to the last archived WAL segment |
| **RTO** (max downtime) | **≤ 4 hours** | Full restore, verify, resume |

Five minutes is chosen because the platform records cash handed over in person. A longer
RPO means a collector's morning collections can be lost with no way to reconstruct them
— the members paid, and there is no record.

### 8.3 Restoration, tested

| Requirement | Detail |
|---|---|
| DEP-RES-001 | **A restore is performed and verified on a scheduled cadence — at minimum monthly, and after any change to the backup configuration.** |
| DEP-RES-002 | Verification is not "the restore completed". It is: row counts match, the ledger balances, and a sample of known transactions reconstructs to the expected balances. |
| DEP-RES-003 | The restore drill is timed, and the measured RTO is recorded. An RTO that has never been measured is a target, not a capability. |
| DEP-RES-004 | The drill is performed by restoring into an isolated environment, never over production. |
| DEP-RES-005 | Restore results — date, duration, discrepancies — are recorded, and discrepancies are treated as incidents. |

DEP-RES-002 is the whole requirement. A restore that produces a database which starts
successfully but whose ledger does not balance has restored the wrong thing, and the
only way to know is to check the arithmetic.

### 8.4 Disaster scenarios

| Scenario | Response |
|---|---|
| Primary database failure | Failover to replica; promote; verify ledger integrity before resuming writes |
| Region outage | Restore from cross-region backup; RTO applies |
| Accidental data corruption | Point-in-time recovery to just before the event; identify the cause before resuming |
| Ransomware / destructive compromise | Restore from the isolated backup account; rotate **all** credentials before resuming |
| Payment provider outage | Queue and retry; collectors continue recording cash; reconcile when the provider returns |

That last row matters for this platform specifically: **a payment provider outage does
not stop the business.** Cash collection continues offline (§35), and the platform's job
is to record it faithfully and reconcile later — which is exactly what the ledger is
built to make possible.

## 9. Scaling path (§39)

Introduced in order, each when a measurement demands it:

| Stage | Change | Trigger |
|---|---|---|
| 1 | Vertical database scaling; connection pooling (PgBouncer) | Connection saturation |
| 2 | Additional `web` instances behind the load balancer | Sustained CPU or latency |
| 3 | Dedicated Celery queues per task class | Financial tasks starved by bulk email |
| 4 | Read replicas for reporting | Report queries affecting transactional latency |
| 5 | Redis caching of read-heavy aggregates | Repeated expensive reads |
| 6 | Object storage + CDN for documents and images | Bandwidth cost, load |
| 7 | Ledger table partitioning by `occurred_at` (03 §14) | Ledger table size |
| 8 | Dedicated reporting infrastructure | Reports competing with operations |
| 9 | Service extraction (02 §7) | A module's scaling profile genuinely diverging |

**§39's discipline: no capacity claim without load testing.** The platform is
*architected* for millions of users; it will not be *described* as supporting millions
until §10 below demonstrates it. §38 is explicit on this and the distinction is not
pedantic — it is the difference between a design intention and a measured fact.

## 10. Load testing (§38)

Performed before large-scale deployment, against progressively larger simulated
populations:

| Stage | Simulated users |
|---|---|
| 1 | 1,000 |
| 2 | 10,000 |
| 3 | 100,000 |
| 4 | 1,000,000+ |

### 10.1 Measured

- API response time (p50, p95, p99) per endpoint class
- Database performance — query latency, lock contention, connection saturation
- Concurrent transactions — throughput and correctness under contention
- Queue processing — depth, latency, drain rate
- Notification throughput
- Payment webhook throughput
- Memory and CPU under sustained load

### 10.2 Scenarios that matter more than raw user count

A million idle users is a much easier problem than eighty-two collectors recording
simultaneously at 7am, which is the shape of this platform's real load. The scenarios
are therefore workload-shaped, not just headcount-shaped:

| Scenario | Why |
|---|---|
| **Morning collection spike** | Thousands of collectors recording within a short window — the platform's peak |
| **Settlement batch** | Many settlements submitted and verified in the same evening window |
| **Contribution reminder fan-out** | Scheduled Celery work hitting a large fraction of members at once |
| **Concurrent disbursement approvals** | Contention on group balance rows — the `select_for_update()` path under real load |
| **Webhook burst** | A provider delivering a backlog after an outage |
| **Offline sync storm** | Many devices reconnecting after a network outage and flushing queues simultaneously |
| **Ledger read under write load** | Balance queries while contributions are being posted |

The last two are the scenarios this platform has that a generic SaaS does not, and they
are the ones most likely to find a real problem.

### 10.3 Correctness under load, not only speed

Load tests assert **financial correctness**, not just latency. After a load run:
the ledger balances, no transaction is unbalanced, no idempotency key was double-used,
and computed balances match the ledger. A system that is fast and wrong has failed the
test.

## 11. Go-live checklist

Before production launch:

- [ ] All CI gates configured and enforced on the remote (11 §6)
- [ ] Staging mirrors production topology and has passed the full suite
- [ ] **Payment provider and SMS/email sandboxes exercised end to end** — a mock proves
      the abstraction, not the integration (13 §11)
- [ ] Secrets rotated to production-only values; no development secret reaches production
- [ ] `DEBUG = False`, asserted at boot
- [ ] TLS, HSTS, secure headers verified against a live scan (10 §6.3)
- [ ] Rate limits configured and load-verified
- [ ] Monitoring and alerts live, with financial-integrity alerts at P1
- [ ] Log shipping verified, with the application unable to rewrite shipped logs
- [ ] Backups running; **a restore drill performed and timed**
- [ ] RPO and RTO measured, not assumed
- [ ] Load testing completed at the target population, with correctness assertions passing
- [ ] Rollback rehearsed
- [ ] Runbooks written: payment provider outage, database failover, queue backlog, suspected compromise
- [ ] **Regulatory review completed** (14_REGULATORY_CHECKLIST) — §45 requires a Nigerian
      legal and regulatory review before production launch, and no software milestone
      substitutes for it
